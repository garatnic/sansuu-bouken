# 算数ぼうけん GitHub運用方針

更新日：2026-10-25

## 基本方針
- **GitHubをソースコード・仕様書の正本**とする。通常の開発ではZIPを受け渡さず、展開したHTML・JavaScript・JSON・CSV・Markdown・TXTをファイル単位で管理する。
- 作業開始時はGitHub上の最新版を確認し、必要なソースと関連仕様書を読んでから変更する。
- GitHubとChatGPTプロジェクトの「情報源」は自動同期されない。両方にある資料に差異があれば確認し、正本はGitHubとする。

## リポジトリ・公開先
- リポジトリ：https://github.com/garatnic/sansuu-bouken
- ブランチ：`main`
- ゲーム配置：`bouken/`
- 公開URL：https://garatnic.github.io/sansuu-bouken/bouken/
- GitHub Pages設定：`Deploy from a branch` → `main` → `/(root)`
- **現行バージョンは必ずGitHub上の `bouken/common/version.js` の `window.BoukenVersion` を直接確認する。運用手順の記述、ToDo、過去の会話や画面表示のバージョンは正本ではない。**

## 開発・更新の流れ
1. ChatGPTがGitHubから最新のコード・仕様・バージョンを確認する。
2. 必要な既存ファイルを編集し、必要なら新しいJS・HTML・JSON・TXT・MDなどを作成する。
3. 新規JSの読み込み元HTMLなど、関連ファイルも忘れず修正する。
4. 可能な範囲で構文・参照・整合性を確認する。
5. **コードの変更と同時に、関連する仕様書・`bouken/siyou/todo.txt`・変更履歴を更新し、矛盾がないか確認する。**
6. GitHubにコミットし、変更ファイル・コミット内容・未検証事項を報告する。
7. **Vercelへのデプロイを実施・確認する。** GitHub連携による自動デプロイを基本とし、対象コミットの反映と公開先を確認する。ChatGPT側に権限がない場合は操作できないことを伝え、Vercel管理画面での確認・再デプロイ方法を案内する。未確認なら成功と断定しない。
8. 必要に応じてGitHub Pagesの公開反映も確認する。PagesとVercelは別の公開環境として扱う。
9. **バージョン更新のたびに、チェックボックス形式の動作確認一覧を提示し、最後に自由記述のコメント欄を設ける。** 新機能・画面遷移・スマホ表示・保存再開・関連既存機能を必要に応じて確認する。
10. ユーザーの確認結果を受け、不具合修正または検証OKの記録をToDo・検証履歴に反映する。

**コミット成功、Vercelデプロイ成功、Pagesデプロイ成功、実機動作確認はそれぞれ別物。未実施の検証を実施済みと報告しない。**

## バージョン・履歴
- 原則、機能追加・不具合修正の開発単位で `bouken/common/version.js` のバージョンを更新する。
- **作業開始時に必ず同ファイルを読み、現在のバージョンを確定する。** 運用手順に固定の現行バージョンを記載しない。HTMLの `?v=` 等の読み込み番号との整合性も確認する。
- コミットメッセージは変更内容を明記する（例：`ver.22: 複数マス開拓時のバフ発動通知を追加`）。
- 仕様書のみの変更ではゲームのバージョンを維持してよい。
- 不具合発生時はGitHubの履歴を参照し、復旧の影響を確認してから戻す。

## ファイル管理上の注意
- テキスト系ファイルはGitHub連携から新規作成・編集・削除できる。フォルダは配下にファイルを作ることで追加できる。
- 大量の画像やバイナリの追加は別途アップロード操作が必要な場合がある。
- ZIP展開時の日本語ファイル名の文字化け、ファイル欠落に注意する。
- 相対パスや既存フォルダ構成は、必要がなければ変更しない。

## Vercel・公開・セーブデータ・安全性
- Vercel管理画面：https://vercel.com/garatnic/sansuu-bouken
- `main` 更新に連動するVercelの自動デプロイを基本とする。毎回対象コミットが反映されたか確認する。
- 管理画面URLと実際のゲーム公開URLを混同しない。公開URLはデプロイ情報から確認する。
- `main` の更新は通常GitHub Pagesへ自動反映されるが、反映には時間がかかる場合がある。
- ブラウザキャッシュで旧版が表示される場合は再読み込みする。
- セーブデータはブラウザの `localStorage` に保存される。端末・ブラウザ・URLごとに異なり、GitHubには同期されない。
- リポジトリとPagesは公開されるため、秘密情報・パスワード・APIキー・個人情報をコミットしない。

## バージョン更新後の確認票
- **毎回、対象バージョンと公開先を明示し、チェックボックス付き確認項目を提示する。**
- 末尾に必ず**コメント欄（不具合・気づいたこと・端末差など）**を置く。
- 確認待ち・一部未確認・検証OKを区別する。確認OKをもらったらGitHubのToDoへ記録する。

```text
【ver.X 動作確認】
- [ ] 追加・修正機能が期待どおり動く
- [ ] 画面遷移・戻る操作が正しい
- [ ] スマートフォンで問題なく表示・操作できる
- [ ] 保存・再開や関連する既存機能が動く

【コメント欄】
（不具合・気づいた点などを自由に記入）
```

## ChatGPT連携の範囲
- GitHub連携からテキストファイルの作成・更新・削除、コミットなどを行える。
- リポジトリ新規作成やPages管理画面の設定など、連携から実行できない操作はユーザーがGitHubで行う。
- 連携の権限や機能は変わる可能性があるため、必要に応じて確認する。

**運用原則：修正依頼 → GitHubのバージョンファイル・最新版確認 → 実装と関連仕様書・ToDo更新 → コミット → Vercelデプロイ確認（必要ならPagesも確認） → チェックボックス＋コメント欄の確認票 → ユーザー検証 → 結果記録。**

## 資料と確認票の現行運用
- 資料はsiyou/README.mdを入口に、現行仕様・作業状態・検証履歴・原本データを区別する。履歴の「未実装」「待ち」を現行ToDoへ再採用しない。仕様とコードが違うときは承認済みの改定を確認し、根拠なく仕様を変えない。
- 現行版の読み取りはcommon/version.js。資料中の版は監査対象/導入版として明記する。
- 2026-10-24のユーザー指定を優先し、確認票は通常Markdownのチェックリスト（- [ ]）と自由記述コメント欄にする。回答待ちウィジェットや送信フォームを作らない。「全部OK」等の短い返答でも結果を記録する。
- 文書だけの更新はゲーム版を維持できる。ゲームを再検証したと表現せず、コミット/公開反映と資料整合確認を報告する。
- ディレクトリ一覧取得に失敗した場合、既知のbouken/siyou/README.md、todo.txt、ゲーム仕様書.txt、common/version.jsを個別取得できる。必要ならGit Trees APIで同じmain SHAの一覧を取得する。一覧取得失敗だけで資料そのものが存在しないと判断しない。
