## 調査結果の要点

**現行コードを再利用したシミュレーターは作れる。** ただし、おすすめパーティーはスキルごとの点数を足す方式では精度が出ない。共通の抽選枠、Lv上限、開拓の実行順、プレイヤーに見える情報まで含めて評価する必要がある。

全67種を確認し、確率計算・Lv合算・開拓順序について小規模な再現確認も行った。大量の模擬冒険や具体的な最強編成の選定はまだ行っていない。

## 分類の意味

| 分類 | この調査での意味 |
|---|---|
| 独立 | 別条件・別段階で適用され、併用禁止ではない |
| シナジー | 一方が他方の発動機会や成果を増やす |
| 競合 | 同じ確率枠・対象・開拓経路を分け合う |
| 相殺 | 特定条件で、組合せ後の結果が補正前へ戻る |
| 上限 | Lv3、成功率、残りマス、情報の重複などで効果が頭打ちになる |

これらは排他的な分類ではない。同じ組合せに「独立した発動判定」と「実行時の競合」が同時にある。

## 1．同一スキルのLv合算・編成制約

同じIDのLvはパーティー全員分を合計し、**Lv3で上限**となる。

- Lv1＋Lv1＝Lv2
- Lv2＋Lv1＝Lv3
- Lv2＋Lv2＝Lv3
- Lv3＋Lv3＝Lv3

したがって、すでにLv3のスキルを増やしても、そのスキル自体には追加効果がない。

編成できる人数は加入種類数により1～5人。同一キャラクターIDの重複編成は禁止。**パーティー全体に「合計コスト12以下」という制約はない。** 個人のスキル構成を作る際のコストと、編成人数の制約は別。

また、仕様書にある「C01とD01を同一キャラクターへ付けない」等の制約は、**パーティー全体の併用禁止ではない。**

根拠：[party.js L3–5][party]

## 3．特に重要な組合せ

### ① 異なる地形の加護：競合する

地形 $i$ の基本比率を $p_i$、合算Lvを $L_i$ とすると、

$$
d_i=0.1L_i,\quad
x_i=\frac{d_i}{1-p_i-d_i},\quad
P_i=\frac{p_i+x_i}{1+\sum_j x_j}
$$

となる。加護なしの $x_i$ は0。

実コードの`targets()`で確認した値：

| 編成効果 | 草原 | 森林 |
|---|---:|---:|
| 加護なし | 11% | 20% |
| 草原Lv3のみ | 41% | 約13.258% |
| 森Lv3のみ | 6.875% | 50% |
| 草原Lv3＋森Lv3 | **約29.333%** | **約37.942%** |

両方を独立に＋30ポイントする処理ではない。共通の地形面積を分け合う。

その後、整数セル数へ丸め、E08で整形する。施設配置の救済で地形を書き換える場合もあるため、最終マップは目標比率とわずかに異なり得る。

根拠：[worldgen.js L111–120、L167–169][terrain]

### ② お宝と仲間の出現率上昇：競合し、条件付きで相殺する

お宝の基本比率を $c$、C01の追加重みを $a$、D01の追加重みを $b$ とすると、

$$
P(\text{お宝})=\frac{c+a}{1+a+b}
$$

となる。

基本50:50の施設では：

| 効果 | お宝 | 仲間 |
|---|---:|---:|
| 補正なし | 50% | 50% |
| C01 Lv3 | 80% | 20% |
| D01 Lv3 | 20% | 80% |
| 両方Lv3 | **50%** | **50%** |

ここでは相殺する。

ただし、小屋の基本はお宝20%・仲間80%。両方Lv3なら**お宝42.5%・仲間57.5%**になる。したがって「同Lvなら全施設で完全相殺」という扱いは誤り。

根拠：[worldgen.js L164–172][split]

### ③ 異なる収集家：対象ごとに競合する

補正なしでは、各大分類は20品／480品で約4.167%。

C04・博物館補正なし、最初の個体抽選について、実際の重み生成処理を確認すると：

| 効果 | 分類A | 分類B |
|---|---:|---:|
| A収集家Lv3だけ | 約57.407% | 約1.852% |
| A・B収集家ともLv3 | **約36.905%** | **約36.905%** |

Aだけを狙うならB収集家は競合する。一方、AまたはBを集めたいなら、両者を合わせた確率は増える。

したがって、収集家を評価するには「お宝の総個数」だけでなく、**欲しい分類・未所持品・完成間近の小分類**を評価対象にする必要がある。

根拠：[events.js L33–36][events]

### ④ 開拓系：発動判定は独立、実行結果は競合することがある

正解時の順序は概ね、

**通常1マス → A02 → A01 → 該当地形特攻 → A12 → 博物館追加 → A03**

となる。

追加先の隣接候補がなくなると、そのスタックの後続処理が止まる。

小さな人工マップで同じ起点・同じ乱数を使い、実`execute()`で比較したところ、

- A01・地形特攻・A12・博物館追加：追加4マス
- その先頭にA02を追加：A02で2マス開いた後に行き止まりとなり、追加2マス

という局面を再現できた。

**A02が弱いという結論ではない。** 発動量の合計から常に成果を予測できず、スキル追加による単調な強化も保証できない、という意味。

一方、追加開拓やA11はA03の閾値到達を早め、B05の透視回数も増やす。こちらはシナジー。

根拠：[buffs.js L5–8、L24–36][buffs]

### ⑤ 成功率補正：併用できるが、利益は逓減する

C02またはD02の追加重みを $b$、F03を $f$ とすると、博物館補正前の成功率は、

$$
p=\frac{0.6+b+f}{1+b+f}
$$

となる。

- C02／D02 Lv3：90%
- F03 Lv3：75%
- 両方Lv3：約91.304%

90%＋15ポイント＝105%という計算にはならない。

D07の再挑戦率を $r$ とすると、最終勧誘成功率は、

$$
p+(1-p)rp
$$

となる。

- D07 Lv3だけ：84%
- D02 Lv3だけ：90%
- D02＋D07 Lv3：99%
- D02＋D07＋F03 Lv3：約99.244%

D02とD07は併用できるが、成功率が高いほど再挑戦の出番が減る。単純な加算以上のシナジーとして扱うより、**成功率の上限へ近づける組合せ**として評価する方が正確。

博物館の受取済み成功率ボーナスは最後に加算する。1回の判定は最大100%で制限されるが、現在の最大パラメーターでは約94.504%、D07 Lv3込みで約99.698%。

根拠：[events.js L58–64][success]、[collection.js L21–28][collection]

## 4．分類のまとめ

| 組合せ | 分類 | 推薦時の扱い |
|---|---|---|
| 同じスキルを複数人が所持 | 上限 | 合算Lv3を超えた分を加点しない |
| 異なる加護同士 | 競合 | 正規化後の地形比率で評価 |
| C01＋D01 | 競合・条件付き相殺 | 施設ごとの基本比率を使う |
| 異なる収集家同士 | 競合 | 目標分類の集合で評価 |
| C04＋対象収集家 | シナジーになり得る | 未所持品の所属分類に依存 |
| D05＋D06 | 条件次第でシナジー・競合 | D06が既所持の多い分類を優遇すれば、未加入率を下げ得る |
| C02＋C03 | シナジー | 成功する機会×成功後の追加品数 |
| C01＋C02／C03 | シナジー | お宝イベント数×成功率×獲得数 |
| 開拓系＋A03／B05 | シナジー | 実開拓数が後続効果の機会を増やす |
| 地形加護＋対応する地形特攻 | シナジーになり得る | 実際に選ぶ問題マスの地形比率が重要 |
| 透視＋地形特攻 | 行動方針次第でシナジー | 見えた得意地形を優先できる |
| A02＋後続開拓 | 独立判定・経路競合 | マップ上で順番に実行して評価 |
| B01＋B05＋B06 | 併用・情報重複・上限 | 新規情報と既知情報を区別 |
| C02／D02＋F03、D02＋D07 | 併用・逓減・上限 | 最終成功率から評価 |
| D03＋D08＋D09 | 基本数を基準に独立追加 | 他グループを減らさず、追加数の再帰増殖なし |
| C02とD02 | 条件別に独立 | それぞれお宝・仲間イベントだけへ作用 |

なお、**D06がある場合、合算スキルが同じパーティーでも所属大分類が違えば性能が変わる。** 「スキルベクトルが同じなら同じ編成」とまとめる際には注意が必要。

## 5．シミュレーターで再利用できる部分

共通処理はブラウザの表示から十分に分離されている。今回、次のモジュールをDOMなしの環境で読み込めることを確認した。

| 再利用する処理 | 役割 |
|---|---|
| `party.js` | 編成正規化・Lv合算 |
| `worldgen.js` | 地形・施設・イベント・プール生成 |
| `buffs.js` | 開拓・透視・探知 |
| `explore.js` | 開拓可否・移動 |
| `events.js` | 候補抽選・選択・獲得 |
| `collection.js` | 受取済み博物館効果 |
| `progress.js` | 達成・全域開拓報酬 |
| `schema.js` | 初期データ・旧スキル正規化 |

必要になるのは、これらをゲームと同じ順序で呼ぶ薄い実行層。特に、HTML内にある次の接続処理を再現する必要がある。

1. 出発時の編成固定
2. A11・A03・博物館初期開拓・視界処理
3. 正解後の開拓・視界・記録・報酬更新
4. 施設候補の選択とイベント処理

根拠：[worldcreate.html L8–13][departure]、[world.html L25][worldstep]

シミュレーションのセーブは毎回複製し、メモリ内で扱えば、実際のlocalStorageに触れる必要はない。乱数は試行ごとにシードを固定できる。ただし、生成処理は`Math.random()`を直接使うため、隔離した実行環境へシード付き乱数を渡す構成が必要。

**同じシードでも、E08等によって乱数の消費回数が変われば、後続の施設配置まで同一になる保証はない。** 同じシードを使うことと、同じ世界で比較することは区別する。

## 6．4分野の評価設計

主評価は、**同じ正解数の予算でどれだけ成果を出せるか**にするのがおすすめ。加えて、完走するまでの必要正解数も測る。

| 分野 | 主な指標 | 補助指標 |
|---|---|---|
| 開拓 | 一定正解数で開いたマス数、全域開拓までの正解数 | 初期開拓・追加開拓・行き止まりで失われた追加量 |
| お宝 | 新規獲得種類数、目標分類の獲得数 | 総個数、新規完成小分類数 |
| 仲間 | 新規加入種類数 | 総加入数、対象大分類、全域開拓報酬と施設加入の内訳 |
| 探索 | 施設発見までの正解数、施設探索の効率 | 新規透視数、位置探知、矢印・区画情報による行動改善 |

重要なのは次の点。

- **総個数だけでは、C04・D05・収集家・F01／F02の価値が十分に出ない。**
- **透視数だけでは、B04・B07の価値が出ない。**
- 全域開拓して全施設を必ず処理する評価だけでは、探索スキルによる「早く見つける価値」が埋もれる。
- 全域開拓報酬の仲間1体は実収益に含めつつ、施設からの加入とは分ける。[報酬処理][progress]
- 博物館は、完成しただけで効果を増やしてはいけない。現在の受取済み状態を固定するか、受取行動を含む長期評価にするかを明示する。
- A03は累計開拓数に依存するため、初期累計を毎回0にするだけでは実ユーザー向け評価にならない。

**探索の自動操作には「見えている情報」だけを渡す必要がある。**

未発見の施設位置やイベント種別を知っている自動操作では、B02・B03・B04・B07がほぼ不要になる。行動方針は、透視・気配・矢印・区画件数から進む先を決める設計にする。

また、現行ゲームは現在地の隣だけを開拓する方式ではない。**開拓済み領域のどこかに隣接していれば開拓可能で、開拓済みマスへの移動も直接できる。** 通常のRPGのように歩数を仮定すると、別ゲームの評価になる。[移動・開拓条件][explore]

## 7．自動編成探索の進め方

927体から5人を全列挙すると、約**5.64兆通り**。全パーティーへ最初から大量試行する方式は現実的ではない。

設計としては、次の順が適している。

1. **所有仲間・解放人数・博物館状態・目標分類を固定**
2. 合算Lv3とD04の無効果を反映し、候補を整理
3. 同じ有効スキル構成をまとめる。ただしD06使用時は所属大分類集合も比較キーに含める
4. 少数試行とビームサーチ等で候補編成を作る
5. 上位候補だけ試行数を増やす
6. 別の検証用シード群で順位を再確認
7. 4分野の成績とばらつき、推薦理由を表示する

最初から1つの総合点だけへ潰さず、**開拓向け・お宝向け・仲間向け・探索向けと、極端な弱点の少ない総合候補**を残す方が、このゲームのスキル構造に合っている。

今回確認したのは、実装の読取と確率式・Lv合算・開拓順序等の小規模再現。大量の模擬冒険や、具体的な最強編成の選定はまだ行っていない。
